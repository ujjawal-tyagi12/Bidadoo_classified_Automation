## 2. Verified application flow

Logging in lands directly on the Seller Dashboard with the **Listings tab already active**
by default (`/dashboard` with no `?tab=` renders the same Listing Management table as
`/dashboard?tab=listings`).

### Table structure (confirmed columns, left to right)

| Column | Notes |
|---|---|
| Checkbox | Header checkbox + one per row. **Disabled for Draft rows**, enabled for Active rows (see §4). |
| Reference ID | Rendered as a link to `/dashboard/create-equipment?view={id}`. Two real formats observed — see §4. |
| Equipment Name | `{Make} {Model} - {suffix}` as generated by the Create Equipment module. |
| Location | Real state/province name for listings that reached step 2; **"N/A" for Draft listings that never got that far**. |
| Price | Sortable (see §2a — sorting is broken). "N/A" for Draft. |
| **Updated Date** | The sheet calls this "Listed Date" — the real column header is **"Updated Date"**. Sortable (also broken, see §2a). |
| Status | `Draft` renders as plain text; `Active`/other statuses render as a **clickable dropdown** with a chevron (not explored further — out of this module's scope, it's a separate status-change affordance). |
| Action | A "More" (⋮) button opening a menu — **contents depend on the row's status**, see below. |

### Action menu — status-dependent (confirmed live)

- **Draft row:** menu shows only **"Edit Listing"**.
- **Active row:** menu shows **"Edit Listing"**, **"Sell with bidadoo"**, **"View Listing"**.

The sheet's TC13 calls this action "Send Listing to Auction" — the real label is
**"Sell with bidadoo"**, and it does not exist at all for Draft rows.

### Edit Listing (confirmed)

Navigates to `/dashboard/create-equipment?edit={id}` — the **same 5-step wizard** the
Create Equipment module already automates, fully pre-filled from the real listing's data
(Reference ID, Title, Make, Model, Category, Model Year, Serial #, Usage Hours, Usage
Type, and presumably the remaining 4 steps), all 5 step indicators shown as already
complete. This can reuse the existing `CreateEquipmentShellPage`/`AssetInformationPage`/etc.
from the Create Equipment module rather than building new Page Objects from scratch.

### Sell with bidadoo (confirmed — real side effects, handle with care)

Clicking it opens a confirmation dialog:

> **Ready to Sell with bidadoo?**
> By continuing, your classified listing will no longer be visible to the public. Our
> Seller Support team will contact you within one business day to discuss selling
> options. Do you want to continue?
> [Cancel] [Yes, Proceed]

**"Yes, Proceed" was deliberately never clicked during this investigation.** It
unpublishes the listing and triggers a real Seller Support contact workflow — not a
reversible, repeatable action safe for automated test runs. Only the **Cancel** path is
safe to automate (dialog appears with the right copy, Cancel closes it, listing stays
Active/unchanged).

### Checkbox / bulk action (confirmed)

Checking one or more **Active** row checkboxes reveals a new **"Sell with bidadoo"**
button next to "Bulk Upload"/"New Listing" at the top of the panel — the same action as
the per-row menu item, just bulk-applied. Draft row checkboxes are disabled entirely (no
bulk action possible on a Draft listing). This is a real, meaningful checkbox effect, not
just a visual toggle.

### Filter panel (confirmed — significant discrepancies vs. the sheet)

Clicking "Filter" opens a dialog with exactly three groups — **no Location filter exists**:

1. **"Listed On"** — a From/To date range. To is disabled until From is picked, and once
   From is picked, **To's calendar disables every date before From** — there is no way to
   construct an invalid (To-before-From) range through the UI (see §5, TC19).
2. **"Price"** — a **dual-handle slider** (e.g. `$434 – $180,266`, bounds derived from the
   real current listing data), not typed min/max text inputs as the sheet assumes. The
   slider's own bounds make an invalid (min > max) range unconstructible through the UI
   (see §5, TC18).
3. **"Status"** — a single-select dropdown: `Active`, `Draft`, `Expired`, `Sent to Auction`.

Filters are **deep-linkable and API-backed**: applying Status=Active updates the URL to
`?status=Active` and the underlying API call to
`GET .../bd-equipment/v1/equipments/seller?status=Active`, confirmed via
`browser_network_requests`. This means filter scenarios can assert against the real API
response shape, not just the rendered table, and tests can navigate directly to a
pre-filtered URL instead of clicking through the Filter UI every time.

### Unauthorized access (confirmed)

Logging out via the real Profile menu → Logout (with its own "Confirm Logout" dialog),
then navigating directly to `/dashboard?tab=listings`, redirects cleanly to
`/login?callbackUrl=%2Fdashboard`.

### Pagination (confirmed)

"Showing X-Y From Z" + First/Previous/[page] Of [total]/Next/Last + a "Rows per pages"
selector (5/10/25/50). 56 real listings already exist in this account from this session's
prior Create Equipment work, so "many listings" (TC34) is already naturally exercised —
no need to manufacture bulk data for it.

## 2a. Confirmed bug: sorting breaks the table

**Clicking either sort icon (Price or Updated Date) permanently breaks the table.**
Confirmed reproducible on two independent fresh page loads, for both buttons
independently:

- The table drops into a loading skeleton and **never recovers**.
- **Zero new network requests fire** (`browser_network_requests` showed nothing new,
  confirmed after waiting 3–5 seconds both times) — this isn't a slow request, the sort
  click doesn't even trigger a fetch.
- A page reload fully recovers the table; the bug is specific to the sort click itself,
  not a persistent broken state.

This directly invalidates the sheet's TC8/TC9 "sorting works, and I can verify order"
premise. Per this repo's established practice (see the Create Equipment module's §2b —
TC1 stayed red on purpose to expose a real navigation bug rather than being quietly
rewritten around it), the sort scenarios are automated against **real, current behavior**:
clicking sort is asserted to leave the table intact, and the assertion is expected to fail
until the app is fixed. This is a genuine bug worth filing, independent of this
automation work.

## 4. Cross-cutting behavior confirmed

- **Reference ID has two real formats**: user-provided `REF{timestamp}` (when the seller
  fills the optional Reference ID field during creation) or system-generated
  `EQP-{20 uppercase alphanumeric chars}` (when left blank). Both are already produced by
  the existing Create Equipment automation.
- **Checkbox disabled-state is status-driven**, not a fixed property — Draft rows can never
  be bulk-selected.
- **Two independent client-side navigations back-to-back caused a brief `net::ERR_ABORTED`**
  once during exploration (navigating away while mid-edit on the wizard) — retried
  successfully on the next attempt. Not pursued further; if it recurs during automation,
  it's a candidate for the same kind of investigation as the Create Equipment module's §2b.
- **The equipment listing API (`GET .../equipments/seller`) is the same endpoint that
  powers both the dashboard table and the API client already built for the Create
  Equipment module's Faker factory** (`tests/api/restful/clients/`) — no new API client
  category needed, only new methods/params (status, price range, date range) on top of
  what may already partially exist there.

**TC37–TC42 (Regression Testing)** are not built as separate scenarios. Each one asks

## 10. Implementation status

Built and passing. New files: `tests/ui/pages/ListingsPage.ts`,
`tests/ui/actions/ListingsActions.ts`, `tests/ui/step-definitions/listings.steps.ts`,
`tests/ui/features/web/listings.feature`, `data/props/listings.props.ts`,
`data/testdata/listings.json`. `ListingsActions` is registered in
`tests/ui/support/action.fixture.ts`; `LoginActions.logout()` and a mobile-menu-aware
`LoginPage` were added to support the unauthorized-access scenario at this project's
narrow local viewport (see §2).

Full suite run (`npx playwright test --project=bdd tests/ui/features/web/listings.feature`):
**18 passed, 1 failed.** The one failure is the sort-button scenario (TC8/TC9) — see §2a —
left deliberately red since it documents a real, reproducible app bug rather than working
around it.

Three real, reproducible app-level races were found and fixed with bounded retries (not
arbitrary waits) during implementation, confirmed via isolated debug scripts outside the
framework before being treated as real:

- **Status filter dropdown** — selecting an option, and separately Apply itself, can
  silently no-op under fast automated interaction (~1-in-3 on the option selection; rarer
  on Apply, once observed submitting `minPrice=0&maxPrice=0` with the status silently
  dropped). `ListingsActions.filterByStatus` retries the whole select-then-apply-then-verify
  flow up to 3 times.
- **Row action ("More") menu** — the same class of race: the menu can fail to open, or open
  and then close again before a specific item is clicked/checked. `openRowActionMenu`,
  `assertActionMenuItemVisible`, and `clickActionMenuItem` all retry by re-opening the menu.
- **Date range calendar** — the calendar popup can fail to open on click; `openDateCalendar`
  retries the same way. Separately, the disabled-day accessible name pattern differs from the
  selectable one ("Not available ..." vs. "Choose ..."), and the To-field's calendar button
  only becomes enabled a moment after the From date commits — both are now handled explicitly
  rather than assumed.

Two locator bugs were also found and fixed during implementation (not app bugs): the Price
filter's range-text locator was resolving to the static "Price:" label only, never the dollar
amounts; and the Equipment Name table cell truncates to exactly 100 characters (no ellipsis,
confirmed live), so the long-name and special-characters scenarios assert against what the UI
actually renders rather than the full raw string. The Price filter boundary scenario
(TC15/TC32) also moved from hardcoded `434`/`180266` test-data bounds to reading the slider's
live `min`/`max` attributes at test time, since the real bounds shift as listings are
created/removed on this shared QA environment.

## 11. BIDC-298 addendum (Flow Functionality)

BIDC-298's 28 cases were triaged against the existing build rather than automated wholesale —
most (filters, bulk select-to-auction, action menu by status, Bulk Upload's real menu, SQL/XSS
search, unauthorized access) already had equivalent coverage from §7's build, several describe
UI that doesn't exist as written (a min>max price error, a from>to date error, a "special
characters not allowed" search error — all confirmed live: the app structurally prevents the
invalid state instead, e.g. the price slider clamps rather than allowing an inverted range),
and the rest (responsiveness, accessibility, load testing, a from-scratch empty seller account)
are out of scope for this framework for the same reasons given in §7. Six genuinely new,
confirmed-live behaviors were added directly into `listings.feature`/`ListingsActions`/
`ListingsPage` rather than a separate module, tagged `@BIDC298-<n>`:

- **§4 Clear all** — resets and closes the filter panel immediately, no Apply needed.
- **§6 Cancel** — discards a pending, unapplied filter selection.
- **§8 Default page size** — the Rows per pages control defaults to "10".
- **§9 + §20 Status → Expired** — confirmed live: only Active listings expose a status
  trigger, whose only option is "Expired" (applies instantly, no confirmation dialog); an
  Expired listing's action menu is *not* disabled as the sheet claims — it opens normally and
  behaves like Draft (Edit Listing only, confirmed by re-checking with the existing
  Sell-with-bidadoo/View-Listing absence assertions), so §9 and §20 are one scenario.
- **§11 Edit and save** — editing a listing's title (Asset Information step) and price
  (Pricing & Contact Details step) and confirming the change persists back on the Listings
  table. Requires a listing that has actually reached step 3 (a single-step draft's later
  steps aren't navigable) — confirmed live, so this scenario creates a full Active listing via
  the existing multi-step flow rather than a draft.
- **§13 + §14 Reference ID → View → Edit** — clicking a Reference ID opens a read-only "View
  Equipment" mode (disabled Category control, an "Edit" button) that leads into the same Edit
  Listing wizard already covered by §7's pre-fill scenario.

The same click-registration race documented above for the Status filter and row action menu
turned out to be systemic to essentially every custom toggle/stepper control in this app, not
isolated to those two — confirmed live (via the same isolated-script method) on the row status
dropdown, the wizard's step stepper (`CreateEquipmentShellActions.goToStep`, also used by §7's
Edit Listing pre-fill scenario), the Reference ID link, and the date calendar's From-day click
specifically leaving the To button stuck disabled. All now retry the same way. One additional,
real finding while building §11: the wizard step stepper's icon reliably shows "completed"
(ticked) for a step in Edit mode even while that step is the one currently on screen, so
navigation is verified against the step's own heading rather than the icon state.

Full combined suite (`npx playwright test --project=bdd tests/ui/features/web/listings.feature`,
26 scenarios): consistently 22–23 passed across repeated full runs. The sort-button scenario
(TC8/TC9) is always the deliberate failure (§2a). Beyond that, 0–2 scenarios occasionally fail
in a full run despite passing individually and in isolated re-runs — always one of the same
documented click-race scenarios (most often the Status filter), never a new or different
failure. This reflects a real, probabilistic app-level race whose rate rises under the
sustained load of a full 26-scenario run; the retries reduce it substantially but a fully
deterministic pass rate isn't achievable against a genuinely non-deterministic third-party
behavior without an unbounded retry budget, which would violate the per-test timeout instead.
